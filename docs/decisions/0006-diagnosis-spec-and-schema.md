# 0006: 診断仕様とデータスキーマ

- ステータス: 採用
- 日付: 2026-10-13

## 背景

フェーズ 2 では、ローカルのみで「質問に回答する → 回答から診断結果（キャラクター）を作る → 結果を表示する」までを実装する。その前提として、診断の仕様と、`@rpg/domain` で扱うデータの形を決める必要がある。

また、データの形は開発初期に何度も変わることが想定される。変更のたびに修正漏れが起きないよう、変更に強い構成にしておきたい。ただし、将来に備えた抽象化は行わない方針（ルートの `AGENTS.md`）とも両立させる。

## 決定

### 診断仕様

- 質問は 10 問。各質問に 3〜4 個の選択肢があり、選択肢ごとに能力値へ加算・減算する点数（整数）を持つ。
- 能力値は 6 種類: 力（strength）・知力（intelligence）・体力（vitality）・素早さ（agility）・器用さ（dexterity）・運（luck）。値は 1〜100 の整数。
- 回答から能力値を作る手順: 選んだ選択肢の点数を能力値ごとに合計し、質問データから求めた「取りうる最小値〜最大値」を 1〜100 に線形に変換して整数に丸める。
- 職業: 職業ごとに能力値の重み（正の整数）を持つ。能力値と重みの積の合計が最も大きい職業を選ぶ。同点ならデータの並び順で先の職業を選ぶ。重みの合計が大きい職業ほど選ばれやすくなるため、重みの合計は全職業でそろえる。
- スキル: 各スキルは対応する能力値を 1 つ持つ。選ばれた職業のスキル候補から、対応する能力値が高い順に 3 つ選ぶ。同点なら職業のスキル候補の並び順で先のスキルを選ぶ。
- 乱数は使わない。同じ回答からは必ず同じ診断結果になる。
- 名前・二つ名・性格・背景・スキルのフレーバーテキストは AI が書くため、フェーズ 3 で扱う。フェーズ 2 のスキーマには含めない。

職業・スキル・質問の具体的な内容と、変換・選択の実装は後続のプルリクエストで追加する。

### スキーマ変更への備え

仕組みを増やすのではなく、「変更が 1 か所で済み、変更漏れを型チェックとテストで機械的に検出できる」ことで変更に強くする。

- Zod スキーマを唯一の定義とし、型は `z.infer` で導く。
- 能力値の種類は `STAT_KEYS` で 1 回だけ定義し、スキーマと型をそこから作る。能力値を増やすと、すべての能力値を必要とするデータやロジックが型エラーになり、修正漏れに気づける。
- 質問・職業・スキルの具体的な内容はデータとして `src/data/` に置き、ロジックは ID で参照する。職業名などをロジックに直接書かない。
- 診断結果（キャラクター）は職業とスキルを ID で持つ。名前や説明文を変えても結果は壊れない。
- 診断は「得点の集計 → 能力値への変換 → 職業の決定 → スキルの選択」の段階ごとに小さな純粋関数に分け、段階ごとにテストする。
- 参照先の ID が存在するかなど、データ間の整合性はテストで確認する。
- スキーマのバージョン番号と移行処理は、診断結果を保存するフェーズ 3 で追加する。フェーズ 2 では結果を保存しないため、移行が必要な古いデータが存在しない。

### ID の形式

データ間をつなぐ ID は、英小文字で始まるケバブケース（例: `power-strike`、`q1`）とする。選択肢の ID は、同じ質問の中でだけ一意であればよい。

## 検討した代替案

- 質問を 5 段階評価（そう思う〜思わない）にする: 回答はしやすいが、選択肢ごとに複数の能力値へ異なる影響を与えられず、RPG らしい場面設定の質問を作りにくい。
- スキルをシード付き乱数で選ぶ: 結果に変化が出るが、同じ回答でも結果が変わり、シードの保存も必要になる。診断としての納得感と検証のしやすさを優先した。
- スキーマに最初からバージョン番号を持たせる: 保存するデータがない段階では使い道がなく、未使用の仕組みになる。

## 影響

- `@rpg/domain` に `features/character`（能力値・職業・スキル・キャラクター）と `features/questionnaire`（質問・回答）を追加した。機能をまたいで使う ID のスキーマは `src/shared/` に置く。
- フェーズ 3 で AI が書く項目と共有 URL を追加するときは、キャラクターのスキーマを拡張し、保存形式のバージョン管理を新しい ADR で決める。
