# 0003: ブランチ戦略とコミット規約

- ステータス: 採用
- 日付: 2026-10-13

## 背景

少人数（主に 1 人と AI コーディングエージェント）で MVP を短期間で開発する。フェーズ4では GitHub Actions で CI を回し、`main` への取り込みをきっかけに AWS へデプロイする予定である。エージェントが作業単位を迷わず切り出せ、履歴から変更内容を追いやすい運用が必要になる。

## 決定

### ブランチ戦略: GitHub Flow

- `main` は常にリリース可能な状態に保ち、直接コミットしない。初回コミットのみ例外とする。
- 変更ごとに最新の `main` から短命のブランチを作る。名前は `<種別>/<短いケバブケースの説明>` とし、種別はコミットメッセージと同じものを使う（例: `feat/diagnosis-scoring`）。
- 1 ブランチ 1 目的とし、無関係な変更は別ブランチに分ける。
- プッシュ前に `pnpm verify` を実行する。
- プルリクエストで CI が通ってから、squash マージで `main` に取り込む。マージ後はブランチを削除する。
- AI エージェントは、ユーザーの指示があったときだけコミット・プッシュ・プルリクエスト作成を行う。

### コミット規約: Conventional Commits（英語）

- 形式は `<type>(<任意の scope>): <要約>`。
- type は `feat`、`fix`、`refactor`、`test`、`docs`、`chore`、`ci`、`build`、`perf`、`style`。
- scope はパッケージや領域の名前（`domain`、`web`、`backend`、`infra`、`e2e` など）。
- 要約は英語の命令形・小文字始まり・末尾にピリオドなし・72 文字以内。
- 破壊的変更は `!` または `BREAKING CHANGE:` フッターで示す。
- squash マージではプルリクエストのタイトルが `main` のコミットメッセージになるため、タイトルも同じ形式にする。

## 検討した代替案

- Git Flow: `develop` と release ブランチを持つ運用は、定期リリースや複数バージョンの並行保守に向くが、継続的にデプロイする小規模な MVP には手順が重い。
- `main` への直接コミット（トランクベース）: 最も手軽だが、CI を通さずに `main` が壊れうる。`main` をデプロイのきっかけにする方針と相性が悪い。

## 影響

- フェーズ4で GitHub の `main` にブランチ保護（プルリクエスト必須、CI 必須、squash マージのみ許可）を設定する。
- コミットメッセージを英語にするのは、エージェントが履歴を読み書きすることを前提としたため（[ADR 0002](0002-documentation-language-and-jsdoc.md) の言語方針に合わせる）。
