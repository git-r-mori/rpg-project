# 0007: ADR に記録する範囲と粒度

- ステータス: 採用
- 日付: 2026-10-14

## 背景

開発は 1 人と AI コーディングエージェントで進めており、ADR の読み手は「未来の自分」とエージェントに限られる。エージェントが普段従うのは `AGENTS.md` と `.cursor/rules/` で、ADR を毎回読むわけではない。

これまでの ADR には、判断の理由に加えて、手順や仕様の細部（実装フローの各ステップ、診断の変換式、ライブラリのバージョン一覧など）も書いていた。その結果、次の問題が起きつつあった。

- `AGENTS.md` やルールと内容が重複し、片方だけ更新されて食い違うおそれがある。
- バランス調整のような日常的な変更でも、ADR の置き換えが必要になってしまう。

## 決定

### ADR を書く条件

次のどれかに当てはまる判断だけを ADR にする。

1. 覆すコストが高い（保存データの形式、共有 URL の ID 方式、インフラ構成、ライセンスや公開範囲など）。
2. 比較して却下した案があり、後から同じ案が再び提案されうる。
3. 一般的なやり方から意図的に外れている、または制約を課している（バージョンの固定、ゲームの数値を AI に決めさせない など）。

迷ったときは「半年後の自分やエージェントが『なぜこうなっているのか、変えてよいか』と聞きそうか」で判断する。

次のものは ADR にしない。

- コードや設定を見れば分かること。
- 手順や規約の細則。`AGENTS.md` と `.cursor/rules/` を正本とする。
- 仕様の細部やゲームバランスの数値。`docs/specs/` やデータ、JSDoc を正本とする。
- ライブラリの小さな選定、リファクタリング、バランス調整。

### ADR に書く内容

- 背景・決定・検討した代替案・影響だけを書き、「なぜ」に集中する。
- 「どうやるか」の詳細は正本へのリンクで示し、書き写さない。

### 既存 ADR の扱い

- ADR は削除せず、統合もしない。判断を覆すときは新しい ADR で置き換え、元の ADR のステータスを更新する。
- 判断を変えない編集（正本と重複する細則を、正本へのリンクに差し替えるなど）は、既存の ADR に直接行ってよい。

## 検討した代替案

- フェーズの区切りなどで古い ADR を統合・削除する: 一覧は短くなるが、当時の前提や却下した案が失われ、同じ議論を繰り返す原因になる。
- 小さな判断も含めてすべて ADR にする: 記録は網羅的になるが、個人開発では書く負担が大きく、正本との重複も増える。

## 影響

- ADR 0001・0002・0003・0004 から、正本と重複していた細則を除き、正本へのリンクに差し替えた。
- ADR 0006 の診断仕様の細部を [診断仕様](../specs/diagnosis.md) に移した。
- ADR を書く条件を、エージェント向けにルートの `AGENTS.md` に記載した。
